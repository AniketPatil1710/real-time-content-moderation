# Architecture.md — Real-Time Content Moderation System

## 1. System Flow

### Training-time flow (offline)
```
Raw datasets (Jigsaw Kaggle CSVs)
        │
        ▼
data pipeline (clean, dedupe, merge, stratified split)
        │
        ▼
processed dataset (train.parquet / val.parquet / test.parquet)
        │
        ├──► TF-IDF + LogisticRegression baseline ──► metrics/baseline.json
        │
        ▼
DistilBERT fine-tuning (HuggingFace Trainer, GPU)
        │
        ▼
models/distilbert-finetuned/  (PyTorch checkpoint)
        │
        ▼
evaluation (PR curves, threshold selection) ──► metrics/distilbert.json, thresholds.json
        │
        ▼
ONNX export (Optimum) ──► INT8 dynamic quantization
        │
        ▼
models/onnx/model_quantized.onnx  +  accuracy re-verification  +  latency benchmark
```

### Inference-time flow (online, the "real-time" path)
```
Client ──POST /moderate {"text": "..."}──► FastAPI
                                             │
                                             ▼
                                   Tokenizer (fast, HF)
                                             │
                                             ▼
                              ONNX Runtime session (loaded once at startup)
                                             │
                                             ▼
                              Sigmoid → per-label scores
                                             │
                                             ▼
                              Threshold logic (thresholds.json)
                                             │
                                             ▼
              {"scores": {...}, "decision": "allow|flag|block", "latency_ms": 23.4}
```

**Decision logic:** max label score < flag_threshold → allow; between flag and block thresholds → flag (human review queue in a real system); ≥ block_threshold → block. Thresholds are per-label, chosen from PR curves during evaluation, stored in `configs/thresholds.json` — never hardcoded.

## 3. Tech Stack

| Layer | Choice | Why |
|-------|--------|-----|
| Language | Python 3.10+ | Ecosystem standard |
| Data | pandas, pyarrow, scikit-learn | CSV → parquet, splits, baseline |
| Model | HuggingFace `transformers` (distilbert-base-uncased) | 40% smaller than BERT, ~97% of quality — the right size/speed tradeoff for <50ms |
| Training | HF `Trainer` + PyTorch, `torch.nn.BCEWithLogitsLoss(pos_weight=...)` | Multi-label + imbalance handling |
| Export/Optimization | HuggingFace `optimum[onnxruntime]` | One-line ONNX export + quantization, maintained by HF |
| Inference runtime | `onnxruntime` (CPU) | The core of the latency story |
| API | FastAPI + uvicorn + pydantic | Async, typed, auto OpenAPI docs |
| Demo | Streamlit | Already familiar from thesis work; fast to build |
| Testing | pytest | Standard |
| Config | YAML + JSON files in `configs/` | No magic numbers in code |
| Experiment tracking | JSON files in `metrics/` (committed) | Zero-dependency reproducibility; W&B optional later |

## 4. Key Architectural Decisions

1. **ONNX session is a module-level singleton** in `serving/inference.py`, created in FastAPI's lifespan handler — never per-request. Per-request loading would blow the latency budget by 100x.
2. **Tokenizer max_length = 128.** Covers >95% of social media comments; sequence length is the dominant latency factor.
3. **Multi-label, not multi-class:** one comment can be both `obscene` and `threat`. Sigmoid per label, not softmax.
4. **Evaluation module is model-agnostic:** `evaluate.py` takes a predict-function, so the same code scores baseline, PyTorch, and ONNX models — guaranteeing the comparison table is apples-to-apples.
5. **Thresholds live in config, generated by a script.** The API reads `thresholds.json`; changing the operating point never requires code changes.
6. **`data/` and `models/` are gitignored**; `metrics/` is committed. Anyone can regenerate the big artifacts, but the evidence of results lives in the repo.
